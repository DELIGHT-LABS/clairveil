# Clairveil DApp

Korean version: [README-kr.md](./README-kr.md)

Clairveil DApp is a browser example for testing Clairveil privacy flows with Keplr and MetaMask.

The boundary is intentional:

- **DApp** owns inputs, wallet UI, and result rendering.
- **ClairveilJS** owns privacy logic: note creation, commitments, encrypted notes, note scan, note planning, prover payloads, disclosure encode/decode, and deposit/transfer/withdraw preparation.
- **Optional local server** owns only static serving and local-test helpers such as faucet, local signers, deposit proof generation, relayer broadcast, and admin/auditor test routes.

For a public node deployment, the DApp can run with the static DApp, ClairveilJS, public RPC/REST endpoints, and a prover URL. Deposit also requires a product-provided `DepositCircuit` proof provider, such as a browser/WASM prover or a trusted proof endpoint.

## Key Files

| File | Purpose |
| --- | --- |
| `public/dapp-config.json` | Same-origin static chain profile artifact read by the browser and production gate |
| `public/dapp-config.js` | Fail-closed loader for the static config artifact |
| `public/app.js` | Browser UI and wallet flow |
| `public/app.bundle.js` | Browser bundle generated by `npm run build:dapp` |
| `server.js` | Local test helper server (faucet, local signer...) |
| `.env.example` | Optional environment override template for local/server-backed runs |
| `test/dapp-smoke.test.js` | Boundary and DApp smoke tests |

CI, release builds, and `make dapp-local` install the checked-in
content-addressed ClairveilJS archive under `vendor/`. This keeps local runs
reproducible and independent of a sibling ClairveilJS checkout. Minimal SDK flow
examples live in ClairveilJS at `examples/minimal-keplr-flow.js` and
`examples/minimal-metamask-flow.js`.

## Main Features

- Chain profile dropdown; the default static config exposes Cosmos/Keplr, and EVM/MetaMask profiles can be added when the target chain provides a compatible privacy precompile
- One shared Wallet Session panel
- Transparent balance and public send
- Deposit from transparent balance into veiled notes
- Veiled note scan with spendable-only filtering
- Veiled transfer with note planning and self-transaction guidance
- Feature-gated Cosmos one-proof atomic batch transfer with per-recipient disclosure and output-evidence status
- Withdraw from veiled notes back to a transparent account
- Relay withdraw payload test flow through the local relayer helper
- Disclosure modes: `none`, `public`, `recipient-encrypted`
- Privacy Events and Event Block views
- Local signer, faucet, and auditor/admin test helpers in local mode, including
  typed per-output batch audit disclosure verification

Before showing a spendable balance or preparing a privacy action, the DApp
validates the active node/tree, consensus circuit, asset registry,
audit/disclosure configuration, and reserve. A failed or stale preflight hides
spendable inventory and blocks deposit, transfer, withdraw, and relay withdraw
until it succeeds again.

The current WebApp keeps ordinary 2x2 transfer as its default. Cosmos
one-proof atomic batch transfer is available only when
`serverFeatures.batchTransfer` is enabled; payroll, recipient-file import, and
unattended bulk orchestration remain out of scope. The product boundary is
fixed in [WebApp scope](../../docs/clairveil-web-app-scope.md).

## Architecture

```text
Browser DApp
  -> ClairveilJS browser client
    -> Cosmos REST/RPC
    -> EVM JSON-RPC
    -> Prover HTTP
    -> Keplr / MetaMask

Optional local server
  -> static files
  -> /api/config, /api/health
  -> local faucet
  -> local signer CLI helpers
  -> local/admin auditor helpers
```

The DApp does not send wallet privacy preparation work to the server. Deposit, transfer, withdraw, scan, user disclosure decode, broadcast, and wait are handled by the browser ClairveilJS client.

## Adding Chains

Edit `public/dapp-config.json` to add static chain profiles. The browser fetches
this same-origin artifact only after `/api/health` is absent or unreachable;
the production gate requires `CLAIRVEIL_WEBAPP_CONFIG_URL` to point to this
exact `/dapp-config.json` path for a static deployment. Do not inject a
different runtime profile through JavaScript. The checked-in static default
exposes the Cosmos/Keplr profile only. In local server mode, the server can
return the same profile shape through `/api/config`.

EVM static profile example:

```json
{
  "activeChainProfileId": "my-evm",
  "chainProfiles": [
    {
      "id": "my-evm",
      "label": "My EVM Privacy Chain",
      "chainName": "My EVM Privacy Chain",
      "transport": "evm",
      "wallet": "metamask",
      "chainId": "my-evm-host-1",
      "rpc": "https://cosmos-rpc.example.com",
      "rest": "https://cosmos-rest.example.com",
      "proverUrl": "https://prover.example.com",
      "depositProofUrl": "https://deposit-proof.example.com/v1/prove",
      "accountPrefix": "clair",
      "shieldedPrefix": "clairs",
      "denom": "utoken",
      "displayDenom": "TOKEN",
      "coinDecimals": 18,
      "evmRpc": "https://evm-rpc.example.com",
      "evmChainId": "0x1234",
      "evmChainName": "My EVM Privacy Chain",
      "evmPrivacyPrecompileAddress": "0x100000000000000000000000000000000000000b",
      "evmGasLimit": "0x989680",
      "evmSendGasLimit": "0x5208"
    }
  ]
}
```

Cosmos profile requirements:

- Clairveil privacy module embedded in the chain
- `/clairveil/privacy/v1/*` REST query surface
- Compatible `/clairveil.privacy.v1.MsgDeposit`, `MsgTransfer`, `MsgBatchTransfer`, and `MsgWithdraw`
- Correct account prefix, shielded prefix, denom, and decimals
- Keplr `signDirect` support
- Browser-accessible REST/RPC/prover CORS

EVM profile requirements:

- Browser-accessible EVM JSON-RPC
- Host chain Cosmos REST/RPC for Clairveil privacy events and queries
- Clairveil 0.2 canonical `IPrivacy` precompile ABI: proof-bearing deposit, transfer self-view disclosure plus absolute expiry, and no legacy withdraw output-note fields
- Fixed `evmPrivacyPrecompileAddress` published by the target chain
- Clairveil privacy account prefix for EVM-derived identity material
- Exact reviewed `depositProofUrl` (or a local-only test helper) for the required `DepositCircuit` proof, plus prover support for `/v1/prover/transfer` and `/v1/prover/withdraw`

This DApp does not support arbitrary or legacy EVM privacy ABI shapes. EVM Clairveil chains must use the same 0.2 privacy precompile ABI and payload semantics; it never fills dummy withdraw output fields or silently drops a required proof, self-view disclosure, or expiry.

## Privacy Flow

`Setup Clairveil` signs a root message with Keplr `signArbitrary` or MetaMask `personal_sign`. ClairveilJS derives the wallet privacy material, shielded address, and disclosure public key from that signature.

Wallet connect, chain switching, root setup, and session signing are bound to
the active privacy session and selected chain profile. If the wallet account or
network, or the selected profile, changes while an extension prompt is pending,
the DApp discards that stale result and requires a reconnect. It clears only
the current tab's in-memory identity state; encrypted reservation evidence in
the previous wallet namespace remains available for recovery.

`Deposit` creates a new note, commitment, encrypted note, and required `DepositCircuit` proof in ClairveilJS. Cosmos profiles produce a Keplr sign doc. EVM profiles produce canonical privacy precompile calldata for MetaMask.

`Transfer` scans notes, plans inputs, creates any required self-transaction step, requests a transfer proof from the prover, creates disclosure payloads, and prepares the final Cosmos sign doc or EVM transaction.

`Batch Transfer` is reached from `Add recipient` below ordinary Transfer and
is hidden unless the Cosmos batch feature gate is enabled. It edits
per-recipient amount/address/disclosure rows, previews total, estimated change,
input/output capacity, and calls `prepareTransferBatch(...)` for one proof and
one `MsgBatchTransfer`. One batch is all-or-nothing. Capacity overflow is never
split silently: the user must explicitly choose multiple independent atomic
batches and is warned that earlier batches remain committed if a later batch
fails. After the SDK's fresh authoritative scan prepares the proof, a final
review binds every requested row to the actual total, change, input/output
counts, full recipient, disclosure mode, and recipient-encrypted target
fingerprint before Keplr opens. A payment larger than the current 16-input
capacity is rejected before split approval. Once a split batch is verified,
its completed rows are locked and excluded from every subsequent retry so a
later cancellation or failure cannot submit those payments twice.
Payload/proof checkpoints are AES-GCM encrypted; a new batch is blocked while
an earlier checkpoint remains unresolved. An ambiguous post-broadcast result
is shown as pending reconciliation rather than failed. After inclusion, each
payment shows success only after typed output evidence and every input
nullifier reconcile. If proof preparation stops after its encrypted checkpoint
but before the DApp opens Keplr, no batch transaction has been submitted. The
DApp immediately opens the matching reservation-review flow: it rechecks every
input nullifier and lets the user discard only that local checkpoint before
preparing the batch again. It never labels that pre-wallet failure as an
ambiguous chain submission.

The local/admin Auditor panel groups ordinary transfers and batch transfers by
transaction. Ordinary transfers retain the legacy event-based audit-disclosure
view. A batch's audit disclosure is deliberately not reconstructed from its
raw event: the panel reads its typed `privacy-scan-v2` outputs and verifies one
mandatory audit envelope per output, including output index, commitment, and
full-disclosure digest. `Decode` displays each verified output separately.

`Withdraw` scans spendable notes, plans the withdraw, requests a withdraw proof, and prepares the final Cosmos sign doc or EVM transaction.

`Relay Withdraw` uses ClairveilJS `prepareRelayWithdraw(...)` to create a proof-backed withdraw payload for a relayer. The browser can prepare and Copy this payload in a static deployment; the `Relay` button is only the optional loopback local-helper submission adapter. The local button does not record an external relay handoff: after current chain/nullifier checks it durably records `BroadcastAttempting` immediately before one same-origin request. That keeps the reservation recoverable if the request result is ambiguous, while avoiding the external-handoff state that deliberately cannot be locally submitted again. Copy, download, QR, upload, or any other payload egress records `recordRelayHandoff` and retains the expiry-bound recovery lock. The payload/proof JSON is privacy-sensitive and stays in memory only. Refresh persistence keeps only reconciliation metadata such as payload hash, reservation ids/status, and expiry; relay reservation metadata does not retain raw amounts or recipients. A page reload does not restore payload/proof JSON, amounts, or recipients. On startup the example rebuilds pending relay entries from active IndexedDB reservations, so closing a tab or creating more than five handoffs does not discard expiry/reconcile state. If a payload has already been copied or handed to a relayer, that relayer may still submit it until expiry. A `ProofReady` reservation should not be released by simple TTL expiry or a plain UI cancel; before handoff the DApp replans the reservation, and after handoff the user should relay, refresh, or reconcile the pending payload state. The pending-handoff `Check recovery` action is a verification step, not a cancel button: it releases an expired handoff only after authoritative expiry, input-nullifier, and broadcast evidence checks. If the record has neither a queryable broadcast identity nor durable no-broadcast evidence, the DApp keeps it locked and explains why instead of silently doing nothing.

For a non-relay `ManualReview` reservation with only a sign-doc identity and no queryable submitted/signed-transaction identity, `Review` explains that the wallet request may have stopped before the prompt, been rejected, or been approved while its result was lost. `Cancel reservation and reprepare` is enabled only after the user acknowledges that wallet activity and the explorer show no submission. It rechecks every input nullifier and then moves only the local reservation to `ReplanRequired`; it neither cancels an on-chain transaction nor marks a note spendable directly. The same action is intentionally unavailable for relay payloads and handoffs.

The DApp persists notes, scan cursor, reservations, and relay recovery metadata
only as namespace-separated AES-GCM ciphertext in IndexedDB. The key is derived
from the in-memory root signature with Web Crypto, is non-extractable, and is
not persisted. Reservation writes require Web Locks. If IndexedDB, Web Crypto,
or Web Locks is unavailable, privacy setup fails closed; there is no
`localStorage`, plaintext IndexedDB, or memory fallback. Raw relay payloads,
proofs, amounts, and recipients remain in memory.

ClairveilJS 0.2.0 is a fresh privacy-note-v1 persistence boundary. This example uses separate `v2` namespaces for note cache, IndexedDB reservations, and relay recovery metadata, so it never revives a 0.1 note, lease, or prepared relay snapshot. Existing users receive an empty cache and a full safe rescan after upgrading; there is no compatibility decode path. The example neither reads nor mutates legacy browser records.

## Disclosure Mode

| Mode | Meaning |
| --- | --- |
| `none` | No user disclosure is created. Explorers/events only show private payloads. |
| `public` | The selected fields are written as a public report. No target pubkey is required. |
| `recipient-encrypted` | The selected fields are encrypted so only the disclosure pubkey owner can decode them. |

### Test With Your Own Disclosure Pubkey

1. Connect a wallet and click `Setup Clairveil` to derive your shielded address and disclosure pubkey.
2. In the Wallet Session card, click `Copy` next to `Disclosure pubkey`.
3. In `Transfer (Veiled Send)`, turn on `Advanced`.
4. Set `Disclosure mode` to `recipient-encrypted`.
5. Paste your copied disclosure pubkey into `Disclosure target`.
6. Check the fields you want to reveal, such as `Amount + asset`, `From shielded address`, and `To shielded address`.
7. Send the transfer, then select the matching `shielded_transfer` in `Privacy Events`.
8. Click `조회` in the event detail to decode the user disclosure with your wallet-derived privacy material.

To disclose to someone else, paste that person's disclosure pubkey into `Disclosure target`. A wallet address alone is not enough to create recipient-encrypted disclosure for them.

## Run

Start the local node, prover, and DApp together for a local test:

```bash
# From the repository root:
make dapp-local
```

If `26657`, `1317`, `8080`, or `5173` is already in use, stop the existing process first. Press `Ctrl+C` in this terminal to stop all three local services.

Start a local Clairveil node:

```bash
# From the repository root:
export CLAIRVEIL_HOME=/tmp/clairveil-dapp-local
export CHAIN_ID=clairveil-local-2
make init
source "$CLAIRVEIL_HOME/clairveil.env"
clairveild start \
  --home "$CLAIRVEIL_HOME" \
  --minimum-gas-prices 0uclair \
  --api.enable \
  --api.address tcp://127.0.0.1:1317
```

Start the DApp:

```bash
cd examples/clairveil-dapp
npm ci
CLAIRVEIL_HOME=/tmp/clairveil-dapp-local CHAIN_ID=clairveil-local-2 npm start -- --host 0.0.0.0
```

Open:

```text
http://127.0.0.1:5173
```

When the DApp is bound to `0.0.0.0`, local signer/admin LAN access still requires `CLAIRVEIL_DAPP_ALLOW_LAN_SIGNING=1` or `CLAIRVEIL_DAPP_ALLOW_LAN_ADMIN=1`. The same-origin prover proxy is disabled unless `CLAIRVEIL_DAPP_ENABLE_PROVER_PROXY=1`, and even then serves direct loopback requests only.

## Public Node Mode

```bash
CLAIRVEIL_DAPP_LOCAL_TEST_MODE=0 \
CLAIRVEIL_DAPP_PUBLIC_ORIGIN=https://dapp.example \
CLAIRVEIL_RPC=https://rpc.example \
CLAIRVEIL_REST=https://rest.example \
CLAIRVEIL_PUBLIC_REST_ENDPOINTS=https://rest.example,https://rest-backup.example \
CLAIRVEIL_PROVER_URL=https://prover.example \
npm start
```

In this mode, local signer, faucet, local CLI deposit, auditor test-secret routes, and the same-origin prover proxy are disabled. The server rejects public-mode startup if a prover proxy, server-held prover bearer token, missing/non-HTTPS public origin, or non-HTTPS profile endpoint is configured. Wallet-driven send, transfer, withdraw, scan, and decode still run in the browser through ClairveilJS. Deposit requires a production `DepositCircuit` proof provider; configure an exact reviewed HTTPS `depositProofUrl` in the active profile (or `CLAIRVEIL_PUBLIC_DEPOSIT_PROOF_URL` for this server-backed example). The loopback `/api/deposit/proof` helper is local-test only.
