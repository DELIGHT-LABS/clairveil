- the result of a small actual localnet run confirming that the multi-chunk restart/retry path works with the same implementation

## Attempted 1,000-Item Actual Localnet Rehearsal in Deposit Mode

The attempted command was as follows:

```bash
CLAIRVEIL_PAYROLL_LIVE_WORK_DIR=tmp/reference-payroll-live-localnet-1k \
PAYROLL_ITEM_COUNT=1000 \
PAYROLL_CHUNK_SIZE=20 \
GAS_PRICES=0uclair \
make reference-payroll-live-localnet
```

This run was not completed. It was stopped manually after the preparation stage was found to take an excessive amount of time.

The partial artifact generated by the time the run was stopped was as follows:

```text
tmp/reference-payroll-live-localnet-1k/out/
```

At the time the run was stopped, 10 `deposit-payroll-*.txhash` files had been generated. The final `rehearsal-summary.json`, `payroll-status-after-settle.json`, and `payroll-final-report.json` files were not generated.

## Reason for Stopping

The current actual localnet tutorial prepares the following notes as real chain transactions for each employee:

```text
1 amount note
1 zero dummy note
```

Therefore, a 1,000-item run requires at least 2,000 deposit transactions and deposit proofs before any transfers occur.

During this attempt, the deposit proof/broadcast/wait cycle repeatedly took several seconds of wall-clock time. In the partial run, reaching 10 deposit transactions took approximately 50 seconds. A simple extrapolation at this rate indicates that deposit preparation alone could take more than 2 hours and 30 minutes. An additional 1,000 transfer proofs and 50 `transfer-batch` transactions would then be required.

In conclusion, the actual localnet path in deposit mode is useful for correctness smoke tests and chunk/retry verification, but it is not suitable as a tool for quickly completing a 1,000-item actual localnet full run within a development session. Restart/retry rehearsals with 1,000 or more items use `PAYROLL_SEED_NOTES=1` seed mode.

## Simulation Rehearsal Results

Separately from the 1,000-item actual localnet run, profiles for 1,000 items, 10,000 items, 100,000 items, and 100 companies x 1,000 items were also produced through simulation rehearsals.

The command was as follows:

```bash
make reference-payroll-rehearsal
```

The main results for the 1,000-item scenario were as follows:

```text
proof_count: 1000
tx_envelope_count: 50
estimated_total_seconds: 144.37556125999438
estimated_total_minutes: 2.4062593543332396
payroll_items_per_sec: 6.92638
```

This simulation is intended to estimate the proof count and transaction envelope count in the phase 1 architecture. The actual localnet note preparation cost is separate. The seeded 1,000-item actual localnet run took approximately 8 minutes and 57 seconds of wall-clock time, while the approximately 2 minutes and 24 seconds reported by the simulation is closer to a pure capacity-model estimate. It may therefore differ from the actual execution time, which includes local machine proof logging, chain waits, wallet scans, and settlement overhead.

## Interpretation

The current implementation can verify chunked payroll transfers at the scale of 1,000 items and the restart/retry invariants on localnet.

However, seed mode is a tool that directly constructs genesis commitments and the wallet cache to reduce localnet rehearsal preparation time. It is not how treasury notes are created in production. Staging/testnet or production should use actual deposits, split/merge operations, and operational approval-based note preparation.

A large-scale production rehearsal requires one of the following:

- batch-deposit support for faster bulk deposit preparation
- a runbook that executes a long-running soak test on staging/testnet
- an operational harness that parallelizes note preparation transactions or shards them across multiple treasury accounts
- a rehearsal that connects recursive split/merge operations or the preparation planner to actual workers

## Recommended Next Steps

1. Use `PAYROLL_SEED_NOTES=1` seed mode as the standard for local developer 1,000-item restart/retry rehearsals.
2. Maintain local developer rehearsals with a small multi-chunk actual run of at least `PAYROLL_ITEM_COUNT=4 PAYROLL_CHUNK_SIZE=2`.
3. For 10,000 items or more, consider the results of both the `make reference-payroll-rehearsal` simulation and a staging/testnet soak test.
4. To verify production note preparation performance, run a separate rehearsal for batch deposits, split/merge operations, and the approval-based preparation planner instead of seed mode.
